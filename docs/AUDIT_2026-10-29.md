# DeepDenoiser 2.0.4 — audit and source cleanup

**Date:** 29 October 2026
**Audited baseline:** `b9dcda235f28416b78cfb6df021894ed2ab7e79d` (the delivered 2.0.4 test APK).
**Cleanup branch:** `agent/audit-cleanup-20261029`, based on that commit. This branch is a source-only cleanup; no new APK was built or installed.
**Scope:** targeted review of recording recovery, storage/exports, audio trimming and video output, dependencies, build configuration, and unused project files. This is not a complete security, codec, performance, legal, or physical-device audit.

## Summary

Two **open** issues were reproduced with disposable host-side samples: a recording with inconsistent WAV lengths can be silently relabelled to the shorter actual length, and optional silence trimming does not fade some cut edges. Neither reproducer establishes that the user's phone has lost audio or produced an audible click. The cleanup did not change either runtime behavior; fixes require their own tests and an Android build.

For now, save/share copies of important healthy recordings and results outside the app, and keep the originals. Consider leaving **Trim Silence** off when preserving every pause and avoiding its cut edges matters. Do not uninstall or clear app data to force an upgrade.

## Prioritized findings

### DD-2026-01 — Medium: recording recovery can hide a length mismatch

**Status: open; reproduced against the actual TypeScript function on a host file mock.**
**Locations:** `src/scripts/recordingSafety.ts:73-103`, called from `src/app/history/index.tsx:55-64` and `src/app/recording/index.tsx:372-376`.

`ensureRecordingWavHeader` accepts the recognized fixed 48 kHz mono PCM16 header and, if either declared length differs from the file's actual length, rewrites the header **in the original file** to match the bytes still present. This helps recover an interrupted recording whose header was not finalized. However, it treats a header that declares *more* data than remains the same way: the call returns successfully without warning that the end may be missing. Rewriting also loses the previous length evidence. The function intentionally does not modify the PCM samples that remain, but a write/interruption can affect the original header. A mismatch does not by itself prove why the file is shorter.

**Reproduce:** after the locked install, run `node scripts/audit-recording-header-repro.cjs`. It constructs a disposable finalized WAV declaring 19,200 PCM bytes, truncates it to 17,200, and invokes the actual function. The function returns 17,200 and rewrites the declared sizes to 17,200 without warning; the remaining PCM bytes match. This is a diagnostic observation, **not** a desired-behavior regression test or an Android crash simulation.

**Recommended fix:** after confirming the writer is idle, preserve the original bytes; create and validate a separate repaired copy, and explicitly warn when the declared size exceeds the available data. Cover interrupted/zero-length headers, nonzero mismatches, disk-full/copy failures, concurrent writer safety, partial writes and sample hashes with host and phone tests. Do not delete either original or partial backup on failure.

### DD-2026-02 — Medium: optional silence trim leaves some abrupt edges

**Status: open; reproduced from extracted production Kotlin on the host JVM, not by an Android listening test.**
**Locations:** `AudioProcessor.kt:838-849` and `:969-1008` in `modules/AudioProcessorModule/android/src/main/java/expo/modules/audioprocessormodule/`; default-off setting `src/scripts/silenceTrim.ts:43-48`.

When only one segment remains, the code uses a direct `copyExactly` and bypasses the fade function entirely. With multiple segments it invokes the fade function, but supplies `trimEndSample + 1` as the total; the last segment's end is therefore treated as the end of the original input, so a removed trailing section does not trigger an outer fade. A discontinuity at such a cut **can** cause an audible click; an audible click on the target phone has not been demonstrated. Optional trimming can also remove quiet speech and meaningful pauses, as the UI warns.

**Reproduce:** with Java, `javac`, Kotlin compiler 2.2.20 and the locked Node dependencies installed, run `KOTLINC=/path/to/kotlinc node scripts/audit-silence-trim-repro.cjs` (or put `kotlinc` on `PATH`). The script extracts the actual segment function, copy dispatch and fade functions from the current Kotlin source and compiles them with the actual `PcmIntegrity.java`. For synthetic 48 kHz mono samples at amplitude 20,000, it reports a single segment beginning and ending at 20,000 (no outer fade). A two-segment case begins at 83 (faded) but ends at 20,000 (not faded). It does not run Android codecs or the full app. The script records the current defect and is deliberately not in the normal passing regression suite.

**Recommended fix:** test a deliberately selected fade policy on single and multiple segments, use the real original sample count for the trailing decision, preserve output length except for selected silence, and add exact boundary/sample tests plus OnePlus listening tests. Such a change intentionally changes trimmed samples and must not be presented as bit-identical to 2.0.4. Keep trimming off for an uninterrupted timeline in the meantime.

### DD-2026-03 — Medium: video output is not lossless

**Status: existing behavior, documented here; not changed.**
**Locations:** `src/scripts/formatHandler.ts:343-355`; `AudioProcessor.kt:1121-1124`.

The video path requests mono AAC at **128,000 bit/s** for the cleaned audio before multiplexing. Android codec behavior and the actual output bitrate need a device check. The project also documents that video can omit additional tracks/subtitles/metadata and may re-encode unsupported video at 30 fps. Therefore “same model” or “no new quality reduction” does **not** mean a video result preserves the original multichannel or compressed audio losslessly. Retain the original and compare the exported video. No bitrate or sample-rate change was made in this cleanup.

### DD-2026-04 — Medium: device, backup, privacy and signing checks remain open

**Status: not validated on a device.** A clean Expo prebuild in this audit generated a manifest declaring `android:allowBackup="true"` and permissions including `INTERNET`, media-read permissions and `SYSTEM_ALERT_WINDOW`. Declarations do not prove a permission was granted, that media was uploaded, or that a backup occurred. The separately delivered APK's merged manifest was not re-inspected in this audit. Depending on Android settings, eligible private files may be included in backup/device transfer. No traffic capture, backup/restore trial or permission-flow test was performed; do not promise zero network access from source inspection alone. No backup setting was changed.

The current APK is debug-signed and intended for personal testing. Its certificate matches the delivered 2.0.3/2.0.2 tests, but an actual upgrade, rollback and preservation of private data have not been demonstrated. An owner-controlled production key normally cannot upgrade a debug-signed app in place. Before installing or changing signing keys, export and verify important files; never uninstall or clear app data merely to force installation. See `docs/RELEASE_SIGNING.md`, `docs/PERFORMANCE.md` and `PRIVACY POLICY.md`.

## Cleanup performed

On a separate source branch, removed seven tracked files with no current code/config references:

- The unimported legacy normalizer `src/scripts/AudioProcess.ts`.
- The uninvoked duplicate helper `patches/patch-ort.js`. The active, tested `patches/onnxruntime-react-native+1.24.3.patch` remains intact.
- Five unreferenced images: `android-icon-foreground.png`, `favicon.png`, `splash.png`, `support_me_on_kofi.png`, and `upi-logo.png` — **272,337 source bytes total**. These were not in the Android Metro asset export; this is not an APK-size-saving claim.

Current icon/splash assets, app features, analytics stubs called by the app, native/autolinked dependencies, and the model were retained. We did not remove packages simply because they lack a direct JavaScript import. Source comments in the TypeScript and Kotlin trim code were corrected so they no longer promise that trimming cannot cut quiet speech or that every edge is faded; no runtime statement was changed. The old 1.6 code audit now links to this report and remains a historical record, not a live tracker. The previous 2.0.4 source snapshot and older builds remain available for rollback.

The model still hashes to `ec5ec24059035741763006dfaa6d463cfbbacf496caed5b5599ebe3477f2dd5b` (SHA-256). The delivered [2.0.4 APK](https://drive.google.com/file/d/1si9jpb8-K9uRRQig6K0vbJtewwKe4Iqv/view) and its [matching pre-cleanup source](https://drive.google.com/file/d/1JVDmLO439-cPU3LQcYin-DdAG_TItSr2/view) are unchanged.

## Recommended next steps

1. Prioritize a non-destructive recording recovery change with a warning for shorter-than-declared recordings; test failure/recovery scenarios before building.
2. Fix trim cut-edge handling as a separately measurable behavior change; add exact PCM tests and listen on the target phone. Keep trim off when its cuts are not wanted.
3. On the OnePlus 7, compare representative short/long and quiet recordings, different providers, video sync, share/save, interrupted recording, low storage, notification denial, backup/restore and in-place upgrade using disposable copies. Never test by deleting irreplaceable data.
4. Review the Expo version warning, dependency advisories, backup/permission policy and, if distributing beyond personal tests, model provenance, native notices and owner-controlled signing. Do not change model weights, sample rate or bitrate merely to address audit warnings.
