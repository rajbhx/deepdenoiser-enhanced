# Bug-report follow-up — source changes, not a device validation

The OnePlus 7 report was captured from `com.sayampy.deepdenoiser` **2.0.5 / version code 7** on Android 10. It does not validate 2.0.6 or these later source changes. It contains no identified DeepDenoiser ANR or app-specific crash; separate `com.sayampy.dfdenoise`, SystemUI, ChatGPT and system `media.extractor` failures are not established as caused by DeepDenoiser. Static-screen time buckets and triple-buffer occupancy are not percentages of dropped frames.

## Actionable changes

- **Direct WAV fallback:** code inspection and a host test reproduced an existing conversion error when the Android decoder fails on a WAV and the app falls back to its RIFF parser. PCM16 negative samples were read as unsigned and clipped to positive full scale. The fallback now interprets samples as signed before downmixing. It also writes one bounded block of output per input block instead of writing each output byte separately. The usual Android decoder is still tried first; no system `media.extractor` fix is implied.
- **Old cache keys:** the old decode, denoise and finished-output lookup keys do not record which decoder created them. New keys therefore avoid reusing potentially affected results. Rebuildable stages may be pruned normally; original imports, recordings and previously saved finished outputs are not deleted or automatically repaired. First processing after this change may take longer. Reprocess and listen to a copy of an affected WAV if needed; there is no evidence that every previous output was affected.
- **Decoder resource cleanup:** even if releasing the codec or extractor fails, the remaining resources and output stream are attempted. The original decoding exception is preserved and cleanup failures are attached; a cleanup-only failure still causes the operation to fail. This cannot prevent or repair a crash in Android's separate media service.
- **Fallback staging and logs:** the normal decoder and direct-WAV retry use the same staged PCM path, and the retry warning no longer logs the media URI. The calling processing pipeline continues to remove its own partial stage on failure; originals are not modified.
- **Recording Stop diagnostics:** optional, allowlisted checkpoints identify native Stop, queue drain, original validation, reconciliation, WAV preparation, saving, and whole-file reprocessing. Finished phases have bounded durations; errors are classified without retaining raw messages. Recording behavior and Back guards are unchanged. These checkpoints do not establish the cause of the previously reported Stop/Back issue.

## Diagnostic use and privacy

In a build that contains these changes, go to **Settings → Diagnostics & self-check → Enable saved history** before reproducing a problem. At most 50 structured events are kept locally, with no filenames, paths, media, hashes or raw exceptions, and nothing is uploaded automatically. An unfinished `START` can indicate the last recorded phase, but it does not prove an ANR or identify its cause. Writes are asynchronous and best effort, so events can be lost on sudden termination. Review any diagnostic report before sharing it; separately collected Android bug reports can contain sensitive personal information.

## Verification and limits

Host tests execute the actual extracted Kotlin WAV conversion over every signed 16-bit mono value, signed stereo examples, 8/24/32-bit PCM and float samples; they also verify bounded output writes. An additional test runs the actual RIFF parser against in-memory provider stubs, including padded chunks, truncated input and inaccessible output. Separate host stubs exercise the actual Kotlin decoder cleanup with injected failures. TypeScript/React regressions cover fallback staging, private logging, cache invalidation, and delayed Stop/Back stages. Existing host and bundled-model tests should also run before any build.

These are not tests of Android codecs, providers, lifecycle, storage failure, sound quality, or the target phone. A newly built APK must be identified and verified separately. Do not install it without the owner's request. For device validation, use disposable media and retain backups: compare a WAV with positive and negative samples, exercise both normal decoding and a deliberately forced direct fallback, listen for clipping, test Stop and Back at each stage, and verify that originals survive failures.
